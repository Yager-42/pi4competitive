## 0. 一句话结论

**引入 5 项**：1 个垂直数据包 + 报告决策壳 + 评论分析 + 订阅定时机制 + 交付校验模式。

**砍掉/降级 9 项**（相对第一版）：sellersprite 包、五维评分独立引入、词根决策继承、品牌监控、Listing 健康检查、功能需求验证、Sif 完整模板、真实报告样例、Excel 导出。

## 1. 前置决策（必须先回答）

**产品定位是什么？** 当前项目的形态（前端"竞争情报中心"、evidence 的 brand/source_type 维度、任务强制 competitors≥1、coverage map 报告）是**通用竞品情报平台**；而三个仓库全部是**亚马逊卖家垂直方法论**。

本清单的默认立场：**保持平台通用定位，垂直能力以"行业包"形式按需接入**——这是引入方式，也是风险控制。若产品定位转向"亚马逊卖家工具"，则部分"不引入"项需要重新讨论。

## 2. 引入清单（5 项）

| # | 引入项 | 内容 | 为什么引入 | 依赖与风险 |
|---|--------|------|-----------|-----------|
| 1 | **sorftime 数据包**（P0） | ~12 个工具：类目 Top100/趋势/关键词、产品详情/评论/流量词/趋势、潜力产品、蓝海类目 | 当前唯一"项目完全没有、接缝现成、价值质变"的能力：coverage 引擎的实体×属性单元格从"搜索文本"变"结构化数据" | 外部 SaaS（API key/配额）；SSE 协议客户端 + 字段适配是 1-2 周全 feature，不是配置级工作 |
| 2 | **报告决策壳**（P1） | 写报告时输出 5 段结构：结论+置信度 / 证据链 / 业务影响 / 前 3 行动 / 缺失数据；加 3 条写作纪律：表格后必须跟洞察、Exec Summary 用"数据点→含义→行动"、缺口必须解释原因 | 报告从"综述"变"可执行决策"；与现有 evidence 体系（置信度/来源）天然互补，缺的只是输出壳 | 纯 prompt 成本，无数据依赖 |
| 3 | **评论分析任务**（P1） | 6 维痛点归类（可编程关键词表）→ 服务细分 + 阈值预警（>2%/>5%）→ 双轨建议（产品改进+客服话术） | 竞品分析高频需求；框架量化可测试 | 依赖 #1（评论数据）；刷单检测仅 L1-L3（数据无 VP 字段，L4 做不了） |
| 4 | **订阅定时执行机制**（P1） | 给 subscriptions 补 scheduler（现代码注释明确 no scheduler） | 这是项目 roadmap 自有的"真监控"待办，不是三仓引入；三仓只提供监控场景参考 | 无外部依赖；定时器生命周期/资源控制需设计 |
| 5 | **交付校验模式**（P2） | 借鉴 evals.json + validate_deliverables：交付物缺失算未完成 | 与项目 O1-O16 测试文化一致，每个新任务类型配门禁 | 轻量，无风险 |

## 4. 不引入清单（含第一版已收回项）

| # | 不引入项 | 来源 | 原因（二次确认后） |
|---|----------|------|-------------------|
| 1 | **sellersprite 数据包**（第一版 P0 → 收回） | sorftime | 与 sorftime 重叠度高（市场/关键词/评论）；43 工具取 8 个仍需独立适配；两家并行 = 双倍账号依赖 + 双倍适配成本。**先单源验证价值** |
| 2 | **五维评分 / Go-No-Go 独立引入**（第一版 P1 → 收回） | sorftime、amazon-skills | 评分标准锚定亚马逊数据（$10M 月销、CR3、Amazon 自营占比）；没有 #1 数据源时 LLM 只能猜数字 = 伪精确。**降为 #1 落地后"品类任务"的模板** |
| 3 | **词根决策继承 → judge 确定性化**（第一版 P2 → 收回） | amazon-skills | **范式不匹配**：它是"广告搜索词数值统计"场景的解法（点击/花费/订单样本量门槛），当前项目是"证据语义"场景（文本摘录的 cell 判定是语义判断不是统计判断）；项目已有 mark_unknown 处理证据不足，无"待判定堆积"问题证据。强搬增加复杂度 |
| 4 | **品牌监控独立项**（第一版 P2 → 收回） | eCommerce-Skills | 四源（Reddit/Google News/DDG/YouTube）与现有 tavily 搜索能力重叠；真正增量只有"定时+危机阈值"，而定时机制 #4 尚未存在。**价值并入 #4，不单独立项** |
| 5 | **Listing 健康检查**（第一版 P3 → 收回） | amazon-skills | 需抓 amazon.com 前台（反爬+合规风险）；是卖家运营工具，与竞品情报定位偏离最远 |

| 7 | **Sif 完整 8 段式模板**（第一版 P1 → 裁剪） | sorftime | "7 天验证计划"等段围绕 Sif 广告/流量数据设计，通用研究场景水土不服；**只取 5 段进 #2** |

## 5. 实施顺序（修正后）

| 阶段 | 内容 | 说明 |
|------|------|------|
| **P0** | #1 sorftime 数据包 | 唯一 P0；先确认产品定位 + API key 可获取 |
| **P1** | #4 订阅定时机制 → #2 报告决策壳 → #3 评论分析 | 定时机制是项目自有待办，先行；评论分析等 #1 |
| **P2** | #5 交付校验；评估 #6 渲染重构、#7 价格监控 | 评估项按触发条件单独决策 |

**顺序逻辑**：数据 → 机制 → 模板 → 场景。不跳步（例如评论分析没有 #1 就是空中楼阁；监控没有 #4 就是空谈）。

## 6. 边界与约束（不变）

- **架构边界**：只进 `capability_packages/*` + `competitive_app/`，不碰 `packages/ai|agent`（契约 D8/D16）。
- **流程纪律**：每个引入项正式实施前按 P4 流程立 feature 契约 + plan；#4（订阅定时）涉及 workflow 生命周期设计，需先行 grill。
- **安全**：外部 MCP key 只进 `config/settings.example.yaml` + env（D23）；外部调用走 native sandbox 网络审批。
- **版权**：三仓均 MIT；方法论移植按 Poirot 先例做 attribution。
- **数据源风险**：sorftime 字段需接入时实测验证（其仓库自身文档与实测就有出入，卖家精灵坑清单仅作参考）。
